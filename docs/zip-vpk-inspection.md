# ZIP release inspection (phase 1)

One shared inspector in PSVitaAlive consumes the existing Orbit release snapshot and exact GitHub release tags from canonical apps with no VPK entry. Direct VPK updating remains unchanged. If a release now has a direct VPK, ZIP alternatives are skipped.

The cache lives in data/archive_zip_inspections.json, not in apps/ or generated catalogs. Keys include inspector schema, app ID, expected Title ID, repository, tag, numeric release and asset IDs, asset URL/name/size, updated_at and official SHA-256 if available. Negative results are reused only for that exact identity. A changed release/asset invalidates the lookup. Transient network, integrity and time-budget failures are never cached. Limits/review outcomes are not classified as no VPK.

The inspector uses bounded downloads with redirect validation, fixed temporary names, no extractall or execution, path/link/duplicate checks, CRC inspection, inner size limits, eboot.bin and bounded param.sfo Title ID validation, and SHA-256 of both outer ZIP and matching inner VPK. More than one matching candidate or incomplete inspection requires review. The result is structural validation, not a guarantee of runtime compatibility, malware absence, or redistribution permission.

Up to 24 ZIP downloads and 1,024 MiB per run, max 200 MiB per archive/VPK, 32 release lookups, twelve-minute target budget (sixteen-minute workflow hard cap). Rotating releases and a persistent bounded cache avoid repeated downloads. Manual previews do not write persistent data.

Phase 1 only audits and records candidates; it does not publish extracted VPKs, update app versions or change Game Files. Phase 2 must re-download the exact pinned asset, verify both digests and Title ID, apply redistribution policy, use the existing owned-item/first-creation checkpoint and verify public bytes before atomically changing the canonical Download/VPK entry. Never publish a ZIP URL as VPK. A port requiring separate game data stays unchanged until compatibility is reviewed.

Star Fox Adventures (STFX00001), catalog v0.1.3, upstream v0.2.0 ZIP is the first real candidate. CrossCraft Classic, CrossCraft SurvivalTest and TheXTech use exact tagged ZIP releases and are also candidates. The cache is not proof that their packages contain a VPK until the audit runs.

## Phase 2: verified publication

The existing Archive.org batch now runs the ZIP publication engine under its shared publisher lock. It re-resolves the current trusted release and requires definitive inspection of every ZIP and exactly one matching VPK. It re-downloads only the chosen ZIP, verifies the original and inner SHA-256, and uploads only the unchanged VPK plus a version-specific provenance file. Existing items require confirmed ownership; new items require account-scoped discovery and durable per-file checkpoints. Pending first creations reserve identifiers across the direct and ZIP engines. The canonical VPK link/version/size are committed only after public checksum verification. Existing Game Files, artwork and unrelated metadata are not modified by this engine; the existing media batch can independently preserve artwork. Six publication attempts per run, 1,024 MiB source budget, 25-minute target (30-minute workflow hard cap). Fully attempted checkpoints consume no ZIP download budget. Ambiguous packages, excluded apps, conflicting destinations, and unsupported providers remain review cases. Inspection uses rounds of one unknown ZIP per application (across all its releases), then additional rounds until a budget is exhausted. Updates and Vita-named packages get priority with ordinary candidates interleaved; names never exclude other packages. Publication alternates pending transfers, updates and missing VPKs. Logs distinguish download count, byte and time deferrals. These are upper bounds, not throughput guarantees. No generated catalog is edited directly.

## Immediate ZIP publication and availability notifications

After public byte verification, the official local generator regenerates the three catalogs in publication-only mode (no persistence of unrelated source files). The verified app, checkpoint and generated catalogs are pushed together. The existing notifier runs against that committed catalog before the next ZIP candidate, and its normal workflow remains the fallback. A first usable VPK at the same version is announced once as Homebrew Now Available in the new-homebrew channel; version upgrades still go to the updates channel. Existing mirrors and artwork alone are not announcements. Legacy version-only notification state is migrated without a mass announcement, with an exact historical CrossCraft Classic checkpoint recovery. Pending ZIP transfers are reconciled at the end of the normal batch and every 15 minutes by a narrowly scoped workflow; no new candidate uploads are scheduled by that workflow. The shared publisher lock and full validation remain in place.
